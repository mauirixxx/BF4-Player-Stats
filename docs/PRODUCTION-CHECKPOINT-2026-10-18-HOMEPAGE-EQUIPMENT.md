## Equipment leaderboard

Files: `site/equipment.html`, `api/leaderboard_api.py` (live: `/var/www/bf4playerstats.com/equipment.html`, `/opt/bf4ps-website/api/leaderboard_api.py`).

- Weapon top ten has sortable **Accuracy**, **KPM**, **Kills**; vehicles have sortable **KPM** and **Kills**. Default remains Kills. Sort requests go to the backend and select a genuine top ten from the full matching population, rather than reordering only the ten displayed rows.
- Weapon accuracy = 100 × shots_hit / shots_fired; undefined for fewer than 100 shots, and rejects source records where hits exceed shots fired. KPM = 60 × equipment kills / equipment usage seconds; undefined below 60 seconds. Vehicles and gadgets with no tracked usage time display unavailable KPM. No vehicle accuracy and no equipment-specific K/D are inferred.
- API validates `sort=kills|kpm|accuracy`, rejects vehicle accuracy, and includes sort metric in its leaderboard cache key. Existing platform, search, and pagination are preserved.
- Some Battlelog gadgets (e.g. AA Mine) have kills but zero recorded usage seconds; this is a source-data limitation, **not** a collector error or reason to substitute soldier-wide playtime.
- Existing equipment API has short-lived caching. Confirm DB query plans and rate/load at higher traffic; the code does not include a precomputed materialized ranking table.

Files: `site/index.html`, `api/general_leaderboard.py` (live: `/var/www/bf4playerstats.com/index.html`, `/opt/bf4ps-website/api/general_leaderboard.py`).

- **PLATOON** appears immediately after SOLDIER, using `platoon_soldier_discovery.linked_platoon_id` and `displayed_tag` for the last observed active platoon, not arbitrary historic account memberships.
- Tags are escaped for HTML, displayed with exactly one bracket pair (e.g. `[HIT]`), and blank when no active tag is available. No additional Battlelog requests are generated by rendering this column.

## Homepage refresh decoupling and production incident

Files: `site/index.html`, `api/homepage_summary_export.py`, `api/temp_dashboard_export.py`, `deploy/systemd/bf4ps-homepage-summary.service`, `deploy/systemd/bf4ps-homepage-summary.timer`.

- The five homepage counters are polled by the browser every 60 seconds. Leaderboards load initially and when visitors interact with filters/platform/search, **not** on the 60-second counter tick. Existing health checks run every 15 seconds and may initialize the leaderboard after recovery.
- Incident: the legacy `temp_dashboard_export.py` built a large soldier/equipment payload before writing `homepage-summary.json`. With database growth the export lagged, and the browser repeatedly fetched an old snapshot even though its timer worked.
- Fix: a lightweight independent one-shot `homepage_summary_export.py` reads counts directly from PostgreSQL, atomically writes `/var/www/bf4playerstats.com/homepage-summary.json`, and is triggered by `bf4ps-homepage-summary.timer` every ~60 seconds. The old heavy exporter no longer writes that summary file. It still produces its separate full snapshot for existing consumers.
- The timer and service files are included here for reproducibility. The service reads `BF4PS_DATABASE_URL` from the **existing**, uncommitted `/root/.config/bf4ps/website-production.env` on `tcou`. Deploy only after checking database permissions and systemd paths.
- First new independent export succeeded at 2026-10-18 00:34:15 HST; user subsequently confirmed the homepage counters resumed updating automatically while the leaderboard remained steady. A sustained multi-day service-health soak has **not** been claimed.

## Why detailed-statistics coverage stays near 35%

The platoon collector continuously discovers additional soldier identities and feeds the collector population. Consequently, the **denominator** (indexed soldiers) grows while the stats collectors increase the **numerator** (detailed soldiers). Percentage coverage can remain roughly stable despite real collection progress. This is an observation, **not** proof of an exact rate balance or collector bottleneck. For capacity planning, separately track new identities/day, detailed successes/day, pending queue age, eligible uncollected soldiers, per-node throughput, and source request budget.
