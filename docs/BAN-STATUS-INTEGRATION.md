# Battlefield Agency / BF4DB integration (Alembic 0027)

- `soldier_ban_status` is an optional per-soldier cache. NULL or absent row means unknown. BA and BF4DB are independent.
- `website/api/ban_status.py` is read-only and the dossier requests `/bf4ps-api/ban-status?soldier_id=<id>`; the endpoint checks the exclusion filter and returns unknown for non-PC.
- `website/scripts/refresh_ban_status.py --persona-id <id>` is an explicit one-persona verifier. Use `--dry-run` before enabling writes. It requires `BF4PS_DATABASE_URL`, writes only matching PC soldiers, and retains previously verified provider status when that provider fails.
- Keep the public web DB role SELECT-only. Use a separate restricted write role for the refresh script. No automatic per-view outbound requests.
- BA's historic ban state can be NULL on a confirmed ban. Explicit unknown states are not treated as clean. Lifted states are not active bans. A missing or incomplete ban-list page never establishes clean status.
- BA `/api/ban/` returns player UUIDs but not necessarily BF4 persona IDs; do not claim a bulk import is complete without an authoritative identity mapping. A bulk importer and rate-limited scheduler are future work.
- The migration creates no cache rows. Verify a known-positive PC soldier (persona 941293200, soldier 11711473) after deploying the read endpoint and writing a verified status.

## Bounded production backfill (2026-11-23)

- Agency importer: `website/scripts/import_agency_bans.py`. Fetches `/api/ban/?page=N&size=100`, resolves each Agency UUID through `/api/player/{id_}`, and matches **only** BF4 `personae[].persona_id` to existing PC soldiers. Writes only explicit active bans; no list absence is treated as clean. Defaults to dry-run. `--apply` requires PostgreSQL peer access on `bf4ps-db`. Use `--start-page`, `--pages` (max 100), `--size` (max 100), and `--delay` (min 0.5s) for bounded runs. No timer is installed.
- BF4DB queue: `website/scripts/verify_bf4db_queue.py`. Only checks existing cached Agency UUIDs with missing or older-than-seven-day BF4DB checks. Defaults to dry-run; `--apply` persists independent BF4DB results. API errors or missing explicit booleans never become clean. Use `--limit` (max 500) and `--delay` (min 0.5s). No timer is installed.
- Initial production pilot: 10 Agency bans imported, 10 persona identities resolved, 10 matches; BF4DB attempted 10 and verified 9, one unresolved. Including preexisting Not-ByK, 11 cached BA bans and 10 verified BF4DB statuses. The Agency list reported 61,887 ban records at pilot time; this is not a count of unique BF4 PC personas. A complete import requires paginated continuation, checkpointing, deduplication across pages, and rate-limit/429 handling before enabling unattended operation.
- **Do not run full historical backfill unattended yet.** The bounded scripts are manual pilots; they do not have durable retry/checkpoint state or a dedicated restricted write role. Do not give the public web API write access to this table.

## Restricted local production writer and resumable importer

On `bf4ps-db` only, PostgreSQL role `bf4ps_ban_sync` has `CONNECT` on `bf4_playerstats`, `USAGE` on `public`, `SELECT` on `public.soldiers`, and `SELECT/INSERT/UPDATE` on `public.soldier_ban_status`; it has no table DELETE and no privileges on other application tables. `pg_hba.conf` has a database/role-specific local peer entry preceding the general local peer entry; `pg_ident.conf` maps the local OS `www-data` account to `bf4ps_ban_sync`. Both files have `.pre-ban-sync-20261123` backups. PostgreSQL configuration reload and the mapped connection were tested. No remote CIDR or public API write permission was added.

`website/scripts/agency_backfill_worker.py` runs under the mapped local identity, with an exclusive file lock and atomic JSON checkpoint in `/var/lib/bf4ps-ban-sync`. It commits idempotent updates per matched identity and advances the page checkpoint only after the full page succeeds. Transient HTTP 429/5xx errors use bounded exponential/Retry-After retries. It loops to page 1 after reaching the end of the current list, to account for pagination drift. Failed pages are retried from their start, without incorrectly marking absent soldiers clean. It defaults to a bounded five-page invocation. Use `--max-pages 1 --delay 0.5` for a canary. Do not confuse page completion with the entire ban list being fully synchronized.

## Production schedules (enabled 2026-11-23 UTC)

Both systemd timers are installed on **bf4ps-db only**, not on `tcou` or collectors. The Agency service runs one 100-record page per invocation and resumes its atomic checkpoint; the BF4DB service checks up to 50 stale/unchecked Agency UUIDs. Both run approximately five minutes after the prior service finishes, as `www-data` mapped to the restricted `bf4ps_ban_sync` PostgreSQL role. Service/timer source files are in `deploy/systemd/`. Inspect `systemctl list-timers '*bf4ps*'`, `journalctl -u bf4ps-agency-backfill.service -u bf4ps-bf4db-verify.service`, and `/var/lib/bf4ps-ban-sync/agency-checkpoint.json`. Stop with `systemctl disable --now bf4ps-agency-backfill.timer bf4ps-bf4db-verify.timer`; stop the active services separately if necessary. The scripts do not write FALSE for BA based on list absence, and BF4DB checks do not overwrite BA status.

## On-demand mode (active 2026-11-23; supersedes bulk mirroring)

At the request of the Battlefield Agency operator, **do not mirror the ban list**. Both old bulk-import and BF4DB-sweep timers are disabled and stopped. Their scripts remain only as historical artifacts and must not be scheduled.

The public dossier reads the cached `soldier_ban_status` values. Values checked more than 24 hours ago are shown as unknown until refreshed. When a status is unknown, `tcou` requests a bounded internal refresh from `bf4ps-db` at `192.168.10.66:8770/refresh?soldier_id=...`. That service is bound to the private interface, checks the request source IP against `tcou` and loopback, and verifies only the requested PC persona. It uses the restricted `bf4ps_ban_sync` role and has no bulk download path. Its queue holds up to 64 requests, has one worker, deduplicates in-flight soldiers, and applies per-soldier 5-minute success / 30-minute error cooldowns. The dossier polls up to three times at 3-second intervals to show newly cached results. API failures never become a clean status. The restricted DB role additionally has SELECT on `player_exclusions` to enforce the exclusion check. No schema change beyond Alembic 0027 was required.

Systemd service `bf4ps-ban-on-demand.service` is enabled on `bf4ps-db`; inspect `journalctl -u bf4ps-ban-on-demand.service` for verification results. The historical `bf4ps-agency-backfill.timer` and `bf4ps-bf4db-verify.timer` must remain disabled. The internal listener must never be routed or proxied to the public Internet.
